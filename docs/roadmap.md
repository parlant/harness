## Intentional boundaries & non-goals

- **No daemon BEAM hot-code reloading:** Extensions load once at daemon startup from explicit local artifacts (`<data_dir>/extensions.json`, `H.Extension` API 1). Updating extension code or settings uses cooperative draining restart (`hi daemon restart` / `restart-service`) rather than swapping BEAM bytecode inside a live session daemon.
- **No C/NIF SQLite dependency in `:harness` core:** `H.Storage.File` provides dependency-free CRC32-framed WAL commits and snapshots in pure Elixir/OTP. An optional relational `H.Storage.SQLite` adapter remains deferred behind the `H.Storage` behaviour so core `:harness` stays free of native C/NIF compilers.
- **No mid-attempt `429` pool switching:** Account selection (`H.Accounts` + optional `MultiCodex`) happens before committing an inference attempt's dispatch policy; `429` rate-limit responses have ambiguous provider scope and use durable coordinator retry/wait scheduling rather than silently switching credentials mid-attempt.
- **No untrusted checkout code execution:** Neither the daemon nor any client discovers or executes plugins, hooks, themes, or adapters from a project workspace checkout or model response. Operator-installed extensions, themes, and prompt templates live strictly under `<data_dir>`.

## Future optional work

- **Internet-facing remote transport:** Add mTLS or SSH subsystem framing when running `h-daemon remote-agent` across untrusted public networks rather than loopback, Unix sockets, containers, or private VPNs.
- **Optional relational storage package:** Implement a separate optional SQLite/PostgreSQL `H.Storage` package when external relational queries across raw session entries are needed.

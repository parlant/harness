# Bringing a harness or a tool to hi

Design proposal, not an extension API shipped by `h`. Three different requests sound like “my own harness”; they should not require the same integration.

| Contributor wants to… | Smallest contract | Who runs the work when the terminal exits? |
|---|---|---|
| Keep H durability, change instructions, context bootstrap and tool set | Trusted Mix package implementing `H.Harness` and `H.Tool`; client selects installed profile by ID | H daemon and its supervised workers |
| Use hi's UI with an entirely different agent runtime | Implement a separate backend speaking the documented session/command/view protocol, or adapt it in a local process | That backend; only advertise guarantees it implements |
| Expose one capability from a client application, e.g. the active editor buffer | An installed proxy tool plus an authenticated optional tool host | Daemon owns the task/result; capability is unavailable if its supplying process is gone |

None requires uploading code to the daemon, loading a Rust `.so`, interpreting npm packages in BEAM, or installing another client's UI to read its history.

## 1. Package a profile, don't subclass the session server

[H.Harness](../lib/h/harness.ex) already resolves `nil`/`coding` (and `pi` alias) to [H.Harness.Coding](../lib/h/harness/coding.ex), and accepts a trusted `opts[:harnesses]` map/list. `id/0`, `descriptor/0`, `tools/1`, `bootstrap_agent/3` are the seam. [H.Tool](../lib/h/tool.ex) supplies `name/0`, `description/0`, `parameters_schema/0`, `mutating?/0`, `replay/0`, `execute/2`. `configure.tools` selects names, **not** implementations. `H.Provider` changes inference; `H.ExecutionEnv` changes workspace operations. None replaces the single writer or commit/recovery rules.

Example contributor path (proposed packaging): ship `acme_review` as a path/git dependency of a **daemon distribution**; publish to Hex only when useful. It depends on a compatible `:harness`, not vice versa. `Acme.Review` returns stable ID `acme.review.v1`, descriptor and tool modules, and bootstraps agent defaults/selected tool names using the bound env. `Acme.BufferSummary` supplies a bounded argument schema and plain content/details result. Test with fake provider and disposable env. Operator registers `%{"acme.review.v1" => Acme.Review}`; `hi --harness acme.review.v1` would send `harness_id` **on create**, not change an attached session. Bare H keeps only `coding` installed. Package docs should say what runs where, supported H versions, side effects and removal/upgrade policy.

Small wiring still needed:

- [H.Daemon](../lib/h/daemon.ex) already uses the registry at create and when starting a catalogued session. [H.serve](../lib/h.ex) and [H.Application](../lib/h/application.ex) don't forward a custom registry in their normal boot options. Wire the same validated operator config into HTTP, boot recovery and Phoenix in-VM calls. Reject duplicate canonical IDs/tool names and bootstrap errors cleanly. No untrusted string-to-atom/module resolution.
- Add optional `harness_id` to Rust create request; later add read-only descriptor discovery for a picker. On create-or-attach check the actual returned profile (today an existing matching workspace can attach regardless of requested profile). Never switch profile implicitly. A missing/incompatible recorded profile makes execution unavailable, not “use coding instead”; keep read-only recovery/export in the design. Pin incompatible tool semantics under a new profile/version; keep old packages for outstanding tasks.
- Starter fixture: small profile with one read-only tool + one failure, exercised via `H.Daemon` and then over v1. Assert bootstrap, schema failure, same tool in model spec and execution allowlist, restart with and without package, and cross-client plain result. Add examples/test helpers outside `lib/h/`; promote shared abstractions only after concrete reuse.

## 2. Bring the whole runtime

`hi` needs operations, not H's process tree: select/create an environment-qualified session; subscribe to its view; submit an idempotent command; load earlier visible entries. Put these behind an internal backend boundary with `H v1` and a deterministic fixture backend. Prefer a **separate local adapter executable** exposing the same loopback/UDS wire contract for another language/runtime. Select endpoint and credentials by explicit backend profile; never send H's owner token or remembered session IDs to another backend. No auto-discovery of project executables. No BYO backend dependencies in H. A client embedding H instead can compose a trusted Mix release like Phoenix does now.

Before claiming compatibility: publish language-neutral example frames/commands and conformance vectors (duplicates, conflict, gap, replay→snapshot, stale progress, branch ownership, offline). Baseline H v1 has no capability handshake. Propose optional versioned discovery for backend ID, replay/detach durability, models, tools and supported actions. Known H v1 without discovery uses the documented baseline; unknown backend must opt into a tested profile, not guess semantics from JSON shape. Reject incompatible major; hide optional actions with reasons. A process-bound adapter that cannot survive detach must say so and is **not** an H-durable replacement. Only split/publish an SDK after a second real backend passes the suite.

## 3. Provide a tool without putting a terminal in the agent loop

**First choice:** if code can run independent of the UI, ship the tool module with the profile or have that module invoke an operator-installed, pinned executable via a supervised adapter. A daemon-owned companion keeps working while `hi` is closed. Prefer this to client callbacks. If the data is inherently live (e.g. unsaved IDE buffer), use a separately enabled bridge package. A browser/TUI consuming conversation SSE is *not* a task worker. Otherwise two viewers could both execute the same call.

**Proposed first bridge experiment:** one statically declared `editor_buffer_summary` proxy module (no dynamic module generation), one local editor host, one versioned schema. A private UDS broker in the optional package, not a new public daemon router or a callback URL supplied in a prompt. Sketch of the lifecycle; message names are illustrative:

1. Owner pairs host with a session/workspace and explicit tool allowlist. Issue a short-lived **tool-host-only** credential via a trusted local pairing flow; don't give it the owner API token. Host connects outbound to broker, authenticates, announces `{host_id, protocol_major, tool_name, schema_digest}`. Broker verifies against installed manifest/policy, binds one host generation to that scope, sets expiry and concurrency limit. No host may overwrite `bash`, claim another workspace or mark itself safe to replay. Disconnect/expiry revokes live routing. Persist allowed profile/tool identity and policy version, never sockets, PIDs or credentials. Treat any host with local OS user privileges as trusted code, not a sandbox.
2. The coordinator remains the **only** authority for enabled tool, argument validation, workspace lease (mutating tools), committed intent, attempt and terminal outcome. Enforce the session's effective allowlist at dispatch as well as in the model schema. Manifest says read-only/mutating and safe/unsafe independently; unknown external effects default unsafe. Existing server maps tool names to modules, not per-connection closures. A static proxy fits it. Don't add a dynamic registry to accommodate hypothetical plugins.
3. After intent commit, proxy worker dispatches `{invocation_id, host_generation, tool, scope, args, deadline}`. Bind that opaque one-use ID in the broker to the live worker/attempt; the worker's return is already fenced by `{incarnation, task_id, attempt_id}` in [H.Session.Server](../lib/h/session/server.ex). Current `H.Tool` context has a task ID and `on_output`, **not** a public attempt-token API. Use worker monitoring/lease expiry for the proxy; if stable external deduplication is later required, design that narrow contract explicitly. No durable progress inferred from a socket acknowledgement.
4. Host reports bounded sequenced `progress`, then `result` or `error`. Broker checks binding, expiry, schema, sizes, deadline, one terminal result. Route progress to `on_output`, return normal plain `content/details/is_error/diagnostic` from `execute`; coordinator commits like any other tool. No arbitrary HTML, terminal escapes, credential echo or broadcast tool requests. Generic views suffice; renderers optional. Cap concurrent calls, bytes and rate; close malformed hosts. Cancel on worker death/deadline; host must stop work on loss of lease. Cancellation is best effort once an external effect has started.
5. No eligible host at dispatch → prompt bounded `tool_unavailable` result, not infinite wait. Disconnect after dispatch/daemon restart → outcome may be unknown; record interrupted with persisted partials, do **not** resend unsafe work or reroute to another attached client. A safe retry requires explicit trusted replay policy and matching version/target; a changing unsaved buffer may need a revision precondition, not automatic reread. Ignore stale/duplicate results. Fencing rejects a late result; it cannot undo a filesystem write. Do not enable mutating external hosts until termination/lease expiry and ambiguous side effects have been tested. Long-lived human approvals require a future durable wait/signal design, not a parked socket.

**Merge gate:** a contributor can run a host fixture, attach both `hi` and Phoenix, observe one tool dispatch/result, then kill client/host/daemon at each boundary. Test unauthorized registration, duplicate claims, stale generation, malformed arguments/result, timeout, unsafe no-replay and safe replay independently. Removing the bridge dependency must leave the stock daemon and both clients usable. Defer marketplace, generic plugin lifecycle, remote network transport, arbitrary UI callbacks and MCP integration until an actual package needs them.
